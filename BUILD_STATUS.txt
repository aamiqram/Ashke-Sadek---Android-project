Nov 12, 2026 working tree (awaiting push) - voice process death root-caused and
fixed on-device; updater TLS fixed with bundled roots:

Voice process death (the real root cause, proven on Redmi Note 4):

- The ":voice" process exits were never memory pressure. v1.1.44's hotword
  wiring made sherpa-onnx fatally exit(255) the whole process, two chained
  config bugs: (a) hotwords.txt was staged at an absolute cache path while a
  non-null AssetManager is set - sherpa refuses absolute asset paths; (b) the
  modeling unit was left empty, so utils.cc EncodeHotwords hit a fatal
  ("modelingUnit" unset). The generic low-memory death toast mislabeled this
  on every device.
- Fix: pass the relative asset name "hotwords.txt" (no cache staging) and
  declare the sentencepiece vocab explicitly: setModelingUnit("bpe") +
  setBpeVocab(<model dir>/tokens.txt) - "bpe" matches the file's
  sentencepiece tokens (500-token Bengali vocab); "cjkchar" would be all-OOV
  at word-initial pieces. Out-of-vocabulary hotwords only log a skip warning,
  they do not kill the process.
- Honesty fix: the process-death toast no longer claims a memory cause; it
  now says the voice process stopped unexpectedly and offers a retry.
- Resilience kept and proven: the active voice session is promoted to a
  microphone-type foreground service (notification id=1041) for the session
  duration, and MainActivity silently retries relaunching the :voice process
  (voiceDeathRetries) if it still dies.
- On-device proof (Note 4, Android 7): one process survived the whole session
  (adj 100 while active), voice-model-loaded pssKb~73-80 MB, decode-load
  ratio 0.28-0.33 (3-4x realtime headroom), FGS notification appears during
  the session and is removed after, no hotword-encode errors.
- Accuracy measured with the developer's own voice: a plainly spoken line
  garbled in the transcript ("তার বিনা") yet the fuzzy matcher surfaced the
  exact right song at the top of the suggestions. Sung lines garble harder
  (expected for a 500-token read-speech model on melodic recitation);
  transcript-tuning (fuzzy thresholds, hotword score) deliberately deferred
  until after release - every tweak risks stray matches without data.

Updater TLS (Redmi Note 4 SSL failure):

- Root cause: Android 7 device trust store does not anchor the update
  hosts' chain; v1.1.40's check fails with CertPathValidatorException
  ("Trust anchor for certification path not found").
- Fix: app/src/main/assets/certs/ bundles 12 PEM roots; AppUpdater builds a
  KeyManagerFactory-backed SSLContext merging system CAs with the bundled
  roots (trustedSslFactory) and both HTTP call sites (mirror manifest + APK
  download) use it. Nothing user-visible changes on healthy devices.
- A/B proof on the same Note 4 minutes apart: v1.1.40 logs
  "Update check failed: ...CertPathValidatorException..."; the fixed build
  shows zero AshkeUpdater failures across two launches with the 24h throttle
  cleared (a failure would have logged - onError logs in silent mode too).

Fonts (assets/fonts/, 928 KB total, OFL license bundled):

- Noto Serif Bengali Regular + SemiBold for lyrics, Noto Sans Bengali

  selection needs API 26+, and Android 5-7 must render identically.

  2aca24bf...83b1). Every load falls back to the system typeface, so a
  broken font bundle can never blank the app.
- Fonts.java loads them; label() uses the bundled sans (real medium weight
  replaces faux bold for Bengali labels).
- SerifEmphasisSpan applies the serif's TRUE semibold for Word-source bold
  emphasis; the old StyleSpan(BOLD) forced the system to fake bold over the
  Bengali fallback, smearing emphasized words.
- tests/validate_fonts.py (dependency-free cmap parser, format 4+12) proves
  all four fonts cover every Bengali codepoint used by the catalogue and
  Java sources: 77 codepoints, 4 fonts, all green; validate_catalog.py
  still green.

Uniform type - the user's Word/PDF promise ("all songs same size"):

- History: per-line shrink (v1.1.46) fluctuated lines inside a song; this
  round first made the scale per-song uniform, and the user then reported
  the remaining cross-song variant: big-line songs rendered smaller than
  neighbours, unlike the Word/PDF where one size fits every song.
- Final policy (user chose it): ONE type size for the whole book at the
  reader's chosen size; a line too long for the column wraps at a word
  boundary exactly as Word did. No shrink pass remains - the measurement
  probe, songScale and appliedScale are gone. Wrap continuation honours
  LeadingMarginSpan indents; BREAK_STRATEGY_SIMPLE + no hyphenation keeps

  3-5) renders 23 uniform lines with no wrap needed; song 11 (flagged)
  renders at full 16 with long lines wrapping Word-style; song 14 uniform.

Protected prewarm (warm model survives browsing):

- Three warm-loss mechanisms closed: (1) idle teardown now memory-aware -
  600 s when totalMem >= 2 GiB && availMem >= 256 MB, else the old 120 s;
  (2) the prewarm load now holds foreground rank with an honest loading
  notification ("কণ্ঠ প্রস্তুত হচ্ছে...") and demotes (stopForeground)

Nov 12, 2026 working tree (awaiting push) - dual-mode capture, hardware
effects, landscape rotation (Phase 2 begins):

Voice receiving (the "what I say is what it must hear" round):

- Dual-mode capture: OfflineBengaliVoice gains MODE_SPEECH/MODE_SONG and a
  (Context, captureMode, Listener) constructor. Speech mode keeps
  VOICE_RECOGNITION -> MIC (the CDD's recognizer-tuned source). Song mode
  keeps the room signal untouched: UNPROCESSED (only when
  AudioManager.PROPERTY_SUPPORT_AUDIO_SOURCE_UNPROCESSED is "true") ->
  CAMCORDER -> VOICE_RECOGNITION -> MIC, with no effects attached.
- Key correction no external advice caught: AcousticEchoCanceler cancels
  THIS phone's own loudspeaker playback - correct for speech (music
  another app plays stops masking the reader's voice), catastrophic for
  song capture (it would erase the very signal being recorded). So
  NS+AEC attach only in speech mode; AutomaticGainControl is deliberately
  never attached (the CDD keeps recognition sources AGC-free; pumped gain
  between words is the model's worst input).
- Speech effects: NoiseSuppressor + AcousticEchoCanceler created on the
  capture session, setEnabled(true), state reported via getEnabled(),
  released in the session finally-block. (setEnabled()'s return type is
  not boolean here - `x != null && x.setEnabled(true)` fails to compile;
  report via getEnabled() instead.)
- VoiceRecognitionService EXTRA_MODE ("speech"/"song") + ensureCaptureMode():
  a mode change is the one case where the warm engine is released and
  reloaded (~8 s on the Note 4); ordinary sessions reuse the warm engine
  untouched. A prewarm load caught mid-flight is demoted from foreground
  and its notification removed with it, or it would linger forever.
- New telemetry (tag AshkeShadekVoice): voice-capture source/rate/mode at
  capture start, voice-capture-effects ns=/aec= after attach,
  voice-transcript partial=/final= for every partial and final - the data
  Phase 3 tuning will mine.
- On-device proof (Note 4, Android 7): tap -> instant warm session,
  voice-capture source=6 rate=16000 mode=speech, voice-capture-effects
  ns=on aec=on, decode-load ratio 0.29-0.34 steady. Transcript-accuracy
  tuning waits for tomorrow's SPEAK/SING recordings
  (C:\Projects\AAMI\Ashke-Sadek-Recordings\). Song-mode UI + 300-3400 Hz
  band-pass deliberately deferred until those recordings give tuning data.

Landscape rotation (the reader finally uses the rotated width):

- Root cause of "the app stays portrait in landscape": the manifest never
  locked orientation - rotation recreated the activity (catalog re-parse
  flash, dialogs and voice state dropped) - and the reading column capped
  at 432dp regardless of width.
- Fix: MainActivity now declares configChanges="orientation|screenSize|
  screenLayout|keyboardHidden", so rotation no longer recreates the
  activity. onConfigurationChanged re-mounts by hand once the width moves
  >= 48dp (mid-transition states never thrash): the reader keeps its
  scroll position and re-renders, index re-renders via renderIndex(),
  home/volume/feedback fall back to renderHome(), loading screens are
  left to the catalog callback. lastRenderedWidthPx seeds in onCreate.
- Landscape column: renderReader caps at dp(660) in landscape / dp(432)
  portrait - the rotated width becomes a wider (still book-bounded) page
  instead of dead margins. effectiveReaderTextSizeSp clamps widthScale to
  <= 1: a wider column never inflates the reader's chosen size; only
  narrower-than-standard columns scale down.
- On-device proof (Note 4): portrait -> landscape mid-song: no catalog
  reload (zero new AshkeStartup lines), same song at the same chosen 16sp,
  the two-line song title fits one line wide; rotating back restores the
  reading position.
