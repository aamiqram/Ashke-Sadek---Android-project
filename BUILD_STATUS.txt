Nov 12, 2026 working tree (awaiting push) - voice process death root-caused and
fixed on-device; updater TLS fixed with bundled roots:

Voice process death (the real root cause, proven on Redmi Note 4):

- The ":voice" process exits were never memory pressure. v1.1.44's hotword
  wiring made sherpa-onnx fatally exit(255) the whole process, two chained
  config bugs: (a) hotwords.txt was staged at an absolute cache path while a
  non-null AssetManager is set - sherpa refuses absolute asset paths; (b) the
  modeling unit was left empty, so utils.cc EncodeHotwords hit a fatal
  ("modelingUnit" unset). The generic low-memory death toast mislabeled this
  on every device.
- Fix: pass the relative asset name "hotwords.txt" (no cache staging) and
  declare the sentencepiece vocab explicitly: setModelingUnit("bpe") +
  setBpeVocab(<model dir>/tokens.txt) - "bpe" matches the file's
  sentencepiece tokens (500-token Bengali vocab); "cjkchar" would be all-OOV
  at word-initial pieces. Out-of-vocabulary hotwords only log a skip warning,
  they do not kill the process.
- Honesty fix: the process-death toast no longer claims a memory cause; it
  now says the voice process stopped unexpectedly and offers a retry.
- Resilience kept and proven: the active voice session is promoted to a
  microphone-type foreground service (notification id=1041) for the session
  duration, and MainActivity silently retries relaunching the :voice process
  (voiceDeathRetries) if it still dies.
- On-device proof (Note 4, Android 7): one process survived the whole session
  (adj 100 while active), voice-model-loaded pssKb~73-80 MB, decode-load
  ratio 0.28-0.33 (3-4x realtime headroom), FGS notification appears during
  the session and is removed after, no hotword-encode errors.
- Accuracy measured with the developer's own voice: a plainly spoken line
  garbled in the transcript ("তার বিনা") yet the fuzzy matcher surfaced the
  exact right song at the top of the suggestions. Sung lines garble harder
  (expected for a 500-token read-speech model on melodic recitation);
  transcript-tuning (fuzzy thresholds, hotword score) deliberately deferred
  until after release - every tweak risks stray matches without data.

Updater TLS (Redmi Note 4 SSL failure):

- Root cause: Android 7 device trust store does not anchor the update
  hosts' chain; v1.1.40's check fails with CertPathValidatorException
  ("Trust anchor for certification path not found").
- Fix: app/src/main/assets/certs/ bundles 12 PEM roots; AppUpdater builds a
  KeyManagerFactory-backed SSLContext merging system CAs with the bundled
  roots (trustedSslFactory) and both HTTP call sites (mirror manifest + APK
  download) use it. Nothing user-visible changes on healthy devices.
- A/B proof on the same Note 4 minutes apart: v1.1.40 logs
  "Update check failed: ...CertPathValidatorException..."; the fixed build
  shows zero AshkeUpdater failures across two launches with the 24h throttle
  cleared (a failure would have logged - onError logs in silent mode too).

Voice receiving (the "what I say is what it must hear" round):

- Dual-mode capture: OfflineBengaliVoice gains MODE_SPEECH/MODE_SONG and a

  AudioManager.PROPERTY_SUPPORT_AUDIO_SOURCE_UNPROCESSED is "true") ->
  CAMCORDER -> VOICE_RECOGNITION -> MIC, with no effects attached.
- Key correction no external advice caught: AcousticEchoCanceler cancels
  THIS phone's own loudspeaker playback - correct for speech (music
  another app plays stops masking the reader's voice), catastrophic for
  song capture (it would erase the very signal being recorded). So
  NS+AEC attach only in speech mode; AutomaticGainControl is deliberately
  never attached (the CDD keeps recognition sources AGC-free; pumped gain
  between words is the model's worst input).
- Speech effects: NoiseSuppressor + AcousticEchoCanceler created on the
  capture session, setEnabled(true), state reported via getEnabled(),
  released in the session finally-block. (setEnabled()'s return type is

  report via getEnabled() instead.)

  a mode change is the one case where the warm engine is released and
  reloaded (~8 s on the Note 4); ordinary sessions reuse the warm engine

Phase 2c - in-app self-update works on MIUI / Android 5-7 (fix verified
against the live failure on the Note 4, local build 1.1.50-local/1050):

- Diagnosis from the device's own logcat when the released 1.1.53-beta
  self-update failed on the Redmi Note 4 (MIUI, Android 7): the download,
  SHA-256 check, package-name/version check and signer verification all
  succeeded; MIUI itself rejected the app's programmatic PackageInstaller
  session commit - 'MIUILOG- Install Reject uid: 10459 pkg
  org.ashkeshadek.reader' followed by 'PackageInstaller: Commit of session
  ... failed: Permission Denied'. MIUI's guard only allows market/adb
  installers to commit sessions; every third-party app hits this on
  Android 5-7. The APK was never the problem (adb install of the same
  release APK succeeds; sha256 verified against SHA256SUMS.txt).
- Fix: installVerifiedApk() now branches. Android 8+ keeps the existing
  PackageInstaller session path (stock Android confirms it through the
  'install unknown apps' permission flow, unchanged). Android 5-7 hand
  the verified APK to the platform installer UI instead - the same
  confirm dialog any file manager's APK install shows, which MIUI does
  not block: ACTION_INSTALL_PACKAGE + EXTRA_RETURN_RESULT with a granted
  read URI. API 24/25 pass a content URI from a new tiny hand-rolled
  UpdateApkProvider (read-only, not exported, serves exactly the one
  verified file files/updates/ashke-shadek-update.apk; a file:// URI
  would trip StrictMode on apps targeting N+); API 21-23 pass the file
  path directly. onActivityResult returns the installer's verdict and
  treats it as final for that attempt (OK or cancel both delete the APK
  and the pending record) - resumePendingInstall fires on every
  onResume, so keeping a cancelled record would re-open the installer
  dialog in a loop the instant the user returns to the app.
  resumePendingInstall also now discards the pending file when the
  installed version already matches (the confirm can complete while the
  app is dead).
- No new permissions (REQUEST_INSTALL_PACKAGES was already declared) and
  no new dependencies - the provider is ~90 lines of framework code, so
  the APK stays the same size.

  (typical shared broadband) 46 MB crawls at 15-25 KB/s, and a stalled
  socket sat silently for up to 2 minutes before dying, after which the
  whole file restarted from zero.
- New transport: the APK is downloaded with 4 parallel HTTP range
  connections; a one-byte range probe picks segmented or single-stream
  mode per host. Each slice retries up to 3 times and resumes from the
  bytes already on disk; connect timeout 15 s and read timeout 30 s turn
  silent stalls into quick retries instead of multi-minute hangs. Parts
  persist across app restarts, with a .total marker that discards stale
  parts when the target release changes (a failed slice's own part is
  dropped so the retry refetches it). The per-slice cap and the 250 MiB
  cap are enforced; the SHA-256 + signer verification after download is
  unchanged and remains the final integrity gate.
- Second route: the publish workflow now force-pushes the APK beside
  update.json on the update-mirror orphan branch, so the updater can
  fetch from raw.githubusercontent.com (a different CDN route) and fall
  back to the GitHub release asset. The mirror URL is derived in-app
  from the verified release URL's own filename (never from untrusted
  metadata), and valid parts carry over between routes since the byte
  layout is identical.
- Progress: a shade notification (এশকে ছাদেক আপডেট - ডাউনলোড হচ্ছে… 34%)
  updates every 2 s while the download runs; it is ongoing during the
  download and cleared on completion or failure. When notifications are
  switched off, single-stream mode still toasts every 4 MB.
- Protocol validated against the live release CDN (2026-11-13): the
  range probe answers 206 with the correct Content-Range total, and a
  4-way parallel reassembly of v1.1.56-beta's 46,210,175-byte APK
  matches its published SHA-256. The mirrored APK for already-published
  releases correctly 404s (exercising the asset fallback); the next
  published release carries the mirrored copy.
- Stale release notes in update.json (v1.1.44-era text) were refreshed
  to describe the current download/notification/installer behaviour.
